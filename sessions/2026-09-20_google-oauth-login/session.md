# Session: Google OAuth login (resolves open question #1)

Date: 2026-09-20

Goal: Resolve the auth-mechanism open question from the 2026-09-19 review — "Google OAuth
is permitted for login, just not for Sheets/Drive/Apps Script data access" — update
`CLAUDE.md` accordingly, and implement the login flow.

## What happened

1. Updated `CLAUDE.md`:
   - Section 4 "Explicitly avoid" — narrowed "Any Google API dependency" to specifically
     mean Sheets/Drive/Apps Script data access; Google OAuth for login is explicitly
     carved out as permitted.
   - Section 6 "Identity, scope and authorisation" — added rule 11 recording the decision:
     Google OAuth replaces legacy's free `Session.getActiveUser()` identity, for login
     only; role/scope are still always resolved server-side from the `users` table per
     rule 8, never trusted from the token.
   - Caught and corrected myself mid-edit: I'd initially written "there is no
     self-service signup" into `CLAUDE.md` as if already settled, before actually asking
     the user. Walked that back to an open note before asking, rather than letting an
     invented decision sit in the governing doc.
2. Asked two clarifying questions before writing any auth code (both needed to avoid
   inventing security-relevant behavior legacy never had):
   - **Signup semantics** → user chose **closed roster**: only emails an admin has
     already added to the `users` table can log in; unrecognised emails authenticate
     with Google fine but are then rejected by RMAS. No self-service account creation,
     matching legacy's admin-provisioned roster exactly.
   - **Session mechanism** → user chose **signed httpOnly cookie, DB-resolved role**:
     the cookie carries only a signed user id; every request re-resolves role from the
     `users` table server-side (rule 8 compliance).
3. Implemented:
   - `models/user.py` — `User` (id, email, display_name, `role` enum admin/operator,
     `is_denied`). Replaces `Config.gs`'s `ADMIN_EMAILS`/`NON_ADMIN_EMAILS`/
     `USER_DISPLAY_NAMES`. Party/flow-sector scope tables are explicitly deferred to the
     staging port (open question #5), not bundled in here.
   - `repository/user_repo.py` — `get_user_by_email` (normalizes to lowercase, matching
     legacy's `.trim().toLowerCase()` convention), `get_user_by_id`.
   - `services/scope_service.py` — `is_administrator()`, porting `AuditService.gs`'s
     `isAdministrator_()` deny-overrides-admin logic. Deliberately placed here rather than
     in an `audit_service.py`, correcting the legacy file's own misplaced coupling (flagged
     in the 2026-09-19 review, §1).
   - `routers/deps.py` — `get_current_user`/`require_admin` FastAPI dependencies (HTTP
     concerns only, per the layering rule that services never import `HTTPException`).
   - `routers/auth.py` — `/auth/login` (redirect to Google), `/auth/callback` (exchange
     code, verify ID token, roster lookup, reject unknown emails with 403, set session),
     `/auth/logout`, `/auth/me` (returns only the caller's own identity — never the admin
     list, per rule 10).
   - `schemas/auth.py` — `CurrentUserResponse`.
   - `main.py` — wired `SessionMiddleware` (signed cookie) and the auth router.
   - `alembic.ini` + `migrations/env.py` + `migrations/script.py.mako` +
     `migrations/versions/0001_create_users_table.py` — first real migration, hand-written
     (not autogenerated, since no live DB was reachable with placeholder credentials).
   - `config.py`/`.env.example` — added `GOOGLE_CLIENT_ID`/`SECRET`/`REDIRECT_URI`,
     `POST_LOGIN_REDIRECT`, `SESSION_SECRET_KEY` (loudly marked insecure-by-default).
4. Wrote a small httpx-based adapter (`_HttpxGoogleAuthRequest`/`_HttpxResponse` in
   `routers/auth.py`) instead of adding the `requests` package — `google.auth.transport
   .requests` needs `requests`, but httpx (already a dependency) can satisfy the same
   `google.auth.transport.Request` interface, so no new dependency was needed for that.
   Only `itsdangerous` (required by Starlette's `SessionMiddleware`) was added and
   installed.
5. Tests: `tests/test_scope_service.py` (deny-overrides-admin, all 4 role/deny
   combinations) and `tests/test_auth_flow.py` (login redirects to Google; unknown email
   rejected with 403; known email gets a session and `/me` returns it; bad OAuth state
   rejected with 400; `/me` requires auth; logout clears the session) — Google's endpoints
   are mocked via `monkeypatch`, so these test RMAS's own logic, not Google's service.

## Errors / issues encountered

- `google.auth.transport.requests` failed to import (`ModuleNotFoundError: No module
  named 'requests'`) — fixed by writing the httpx-based adapter instead of adding a new
  dependency (see above).
- First test run of `test_auth_flow.py` failed with `sqlite3.OperationalError: no such
  table: users` — the `sqlite:///:memory:` engine was creating a fresh, separate in-memory
  database per pooled connection, so the table created by the fixture's
  `Base.metadata.create_all()` wasn't visible to the connection the request handler's
  thread pulled from the pool. Fixed by adding `poolclass=StaticPool` so all connections
  share the one in-memory database.
- While sanity-checking the Alembic setup (`alembic check`, which needs a live DB
  connection), discovered **there is an actual Postgres server reachable at
  `localhost:5432`** — it rejected the placeholder `rmas`/`rmas` credentials
  (`password authentication failed`), so it's a real, pre-existing server, not something
  this project stood up. `alembic history` (which doesn't need a live connection)
  confirmed the migration file itself is valid: `<base> -> 0001 (head), create users table`.
