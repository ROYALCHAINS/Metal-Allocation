What the application currently does

RMAS is a working two-stage daily metal-allocation ledger. An operator opens the Daily Allocation screen, enters Today's Required per allocation sector and Today's Acquired per flow party, and submits once — POST /staging/{date} (rmas/services/staging_service.py:188). An administrator opens the same date, sees those figures already overlaid (staging_service.py:122), sets Alloted per sector, and commits — POST /allocations/{date} (rmas/services/allocation_service.py:281).

The server derives previous_requirement from the carry-forward source date and computes balance = previous_requirement + today_required − alloted itself; neither figure is accepted from the client (validation_service.py:252-258). A saved date is immutable except through a reasoned revision, which now also cascades forward through every later saved date and audits each recomputation (allocation_service.py:735, cascade_service.py:98). Four read-only screens exist — Allocation History, Metal Flow History, Analysis Dashboard, and an administrator-only Audit Log with server-built before/after diffs.

Current development phase

Late implementation, pre-verification. The port is functionally near-complete. What remains is operational hardening (one un-applied migration, one authentication hole), browser verification — nothing in this project has ever been looked at in a browser, as every session log states — and closing several documented contradictions.

Main technology stack

Python 3.14.0 · FastAPI 0.141.1 · Pydantic 2.13.5 · SQLAlchemy 2.0.54 · Alembic 1.20.0 · SQLite (rmas/rmas.db) · bcrypt · Starlette SessionMiddleware cookie sessions · pytest 9.1.1 + httpx. The frontend is dependency-free vanilla ES modules — no framework, no bundler, no package.json — served as static files by FastAPI itself (rmas/main.py:66).

Overall project status

13,847 lines of Python across eight layers, 5,801 lines of frontend, 332 passing tests, 26 session logs, five migrations (all applied). Architecture discipline (routers → services → repository → models) holds throughout: no router imports a SQLAlchemy model, and no service opens a Session.

Is it runnable?

Resolved Yes — the database now matches the code.

The original audit found rmas/rmas.db stamped at Alembic revision 0004 while the head was 0005. Migration 0005 adds metal_allocation_audit_log.parent_audit_id, which models/audit.py:98 maps unconditionally, so every audit write failed — and since save, revise and operator submission each write an audit row inside their transaction, all three write paths were broken.

Migration 0005 has since been applied. It was rehearsed on a copy first, because it rebuilds the audit table rather than altering it (SQLite has no ALTER CONSTRAINT, so widening the action_type CHECK means a full table swap on 39 compliance rows). Verified afterwards on the live file: revision 0005 (head), parent_audit_id present, RECALCULATE admitted, both append-only triggers recreated and still aborting UPDATE and DELETE, six indexes including the new idx_audit_parent, no leftover rebuild table, and row counts across all eleven tables identical to the pre-migration backup — with the audit log's 39 rows byte-identical.

One caveat carried forward honestly: a real save and a real revise have not been driven through the API against live data, because that writes actual ledger rows for a real date and increments a real revision number. Schema-level acceptance of a RECALCULATE row carrying a parent_audit_id was confirmed inside a transaction that was rolled back, so nothing was left in the append-only log.

Error handling

Services raise domain exceptions and never import HTTPException; routers own the mapping (allocations.py:73-82, staging.py:36-41). Verified by search: zero HTTPException imports anywhere under services/.

Authentication and authorization

  • Cookie session carries only a signed user_id — main.py:52, deps.py:26.
  • Role and scope are rebuilt from the database on every request — deps.py:43-56. Rule 8 holds.
  • The deny list always overrides an admin grant — scope_service.py:44.
  • Resolved is_active is re-checked on every request, not only at login — deps.py:34. A deactivated account loses its session immediately rather than keeping access until the cookie expires.
  • Scope is applied in the SQL WHERE clause, never post-filtered — sector_repo.py:21, report_repo.py:23, staging_repo.py:25. An operator with zero granted parties fails closed.
  • Every /audit/* route re-checks admin status server-side via require_admin.
  • /allocations/{date}/revise deliberately avoids Depends(require_admin) so the service can write an UNAUTHORIZED_REVISION audit entry first — allocations.py:347-350.
