1 · What this system is

A daily ledger for physical gold moving through a manufacturing floor.

The question it answers

Once per working day: given the metal acquired from each supplying party and the metal required by each manufacturing sector, how much is alloted to each sector, and what carries forward to tomorrow?

Demand may exceed supply

That is not an error. The shortfall becomes the balance and rolls into the next day's opening requirement. A closing balance of zero is equally valid.

Two-stage day

Operators submit requirement and acquisition figures into a staging table. An administrator reviews them, sets the allotment and commits — and only that commit writes the masters and computes a balance.

Everything is audited

Each commit records both the previous and the updated state, the actor, the reason and the request id. The log is append-only, and failed attempts are written to it too.

balance = previous_requirement + today_required − alloted    // kg to exactly 3 decimals, stored as integer grams

Two conventions carried over from the legacy system are worth knowing before reading any of this code. Weights never touch a float — they are integer grams in the database and Decimal in Python, because three decimals of a kilogram is exactly one gram. And the field is spelled alloted, with one l, so that comparisons against historical data still line up.

3 · Feature ledger

Thirteen areas shipped, four partial, five not started, three dropped on purpose.

Shipped

Authentication — username and password

Closed roster, no signup page. Login, logout and session identity work; passwords are bcrypt-hashed and verified in constant time. Accounts are provisioned out of band by an administrator, mirroring how the legacy system was configured by hand.

Shipped

Scope and authorisation

Role and party scope are resolved server-side from the session on every request; a client-supplied party or sector filter is intersected with that scope rather than trusted. A deny entry overrides an admin grant. Operators see only their own party's rows on every screen.

services/scope_service.pyrouters/deps.pytest_scope_service.pytest_sector_scoping.py
Shipped

Weight precision, end to end

One module owns every kilogram-to-gram conversion and refuses a float argument outright rather than converting it silently. Rounding is half-up at the third decimal; comparisons use the legacy epsilon instead of equality. Proven by exact round-trip and accumulation-without-drift tests.

services/weight_service.pylib/format.jstest_weight_service.py
Shipped

Working-week date rules

Monday looks back to Saturday, every other day looks back one day — the six-day week, not a simplification to "yesterday". When nothing was saved on the rule date, the carry-forward falls back to the most recent saved date, so a skipped day never silently resets a balance to zero.

services/date_service.pytest_date_service.py
Shipped

Schema, migrations and reference data

Twelve tables and three presentation-only kilogram views, built from the supplied schema across four Alembic revisions. Five departures from that file are documented in the relevant model's docstring rather than applied silently: a password column, a widened audit action list, a nullable audit date, a corrected staging status vocabulary, and priority stored as text because users see the label unchanged.

Daily Allocation — save path

Admin-only commit. Rows are rebuilt from the database and indexed by sector, so row order cannot corrupt a save and party, purity and priority never come from the client. Writes are serialised per date, guarded by a 900-second request-id window, and both ledgers plus the audit entry commit together; staged rows are then marked consumed.

Operator requirement submission

An operator submits required and acquired figures for their own parties into staging, once per date — a correction has to go through the administrator. Scope comes from the session; the payload carries weights keyed by sector id and nothing else. Submissions, blocked resubmissions and failures all land in the audit log.

Operator submissions on the admin screen

Staged values are merged into the admin's model correctly, and the payload already carries the submission count and the per-operator record of who submitted and when.

Neither is rendered. Legacy shows a banner reading "N operator submission(s) loaded into this date"; nothing surfaces it yet, so the administrator commits figures without being told they came from operators.

Partial

Truncation notices

The audit page computes its truncation flag honestly against the row cap. Both history pages hard-code it to false, following legacy, so the notice that is already wired into the markup can never fire.

The page spec says to raise the history pages to the audit page's behaviour rather than flatten the audit page down to theirs. Not yet done.

Partial

HTTP-level test coverage

Health, auth, sectors, all three audit endpoints, staging submission and the allocation read path are exercised through the real HTTP stack. Dashboard rules are covered at service level only.

No HTTP test for POST /allocations/{date} or for any of the five report endpoints — the exact gap that previously hid an attribute error on the dashboard route.

Not built

Administrator revision of a saved date

The single largest hole, and the only missing write path. A saved date is immutable with no supported way to correct it: there is no service function, no endpoint and no UI. The groundwork is in place — the REVISE and FAILED_REVISION action types exist in the schema, and the reason check (minimum ten characters) and revision numbering are ported and currently unused.

Until this ships, a mistyped allotment can only be corrected in the database by hand, outside the audit trail the system exists to keep.

The one to settle first

The rule-toggle conflict is the only open item that could invalidate data already committed, rather than merely change a screen. If full allocation and positive allotment were always meant to be enforced, every date saved under the permissive rules would need reviewing — and that review needs the revision path, which does not exist yet. The two questions are really one question.
